## [Unreleased]

### Security
- **Potentially breaking: `jwtUnverified` is an explicit opt-in, and the Helm chart verifies tokens wherever OpenID is configured (OMPE-105840, SAST-001).**
  - Since notification-common 7.0.0 the service refuses to start in `jwtUnverified` mode, which reads the publisher's identity from a bearer token without verifying it, unless `OMNI_EVENTS_ALLOW_UNVERIFIED_JWT=true` is also set. The Helm chart never sets that opt-in by itself.
  - The Helm value `principalSource` no longer defaults to `jwtUnverified`; it defaults to empty. An explicit `principalSource` is used as given. Left unset, the chart selects `jwt` when `openId.openIdConfigurationUri` and a JWT audience (`openId.additionalJwtAudience` or the `clientId` of the `default` entry in `openId.clientRegistrations`) are configured, and otherwise fails to render with a message naming both fixes.
  - The chart never selects `jwtUnverified` by itself, not even behind the HTTPProxy's Envoy auth extension: the extension covers only traffic through the HTTPProxy, and the chart's Service (`ClusterIP` by default) is reachable directly from inside the cluster. `jwtUnverified` now renders only when the values set both `principalSource: jwtUnverified` and the new `allowUnverifiedJwt: true`, which is safe only when every path to the pods verifies tokens first, including a NetworkPolicy (or equivalent) that keeps the Service unreachable except through the verifying proxy.
  - The chart fails at render time, rather than as a crash-looping pod, for the other configurations the service refuses at startup: `jwt` without the URI or an audience, `opaque` without the URI, `userInfoService` without `userInfoService.uri`, `disabled` with `permissions.enabled`, `permissions.enabled` without `permissions.endpoint`, more than one `default` client registration, an unknown `principalSource`, an `openId.additionalJwtAudience` that is not a list, and an `allowUnverifiedJwt` that is not a boolean (a quoted `"false"` included).
  - `OMNI_EVENTS_JWT_AUDIENCES` now includes `openId.additionalJwtAudience`, as the Event Consumer Service chart's does, and is rendered only for `jwt` and `opaque`.
  - **Migration:** a deployment that sets OpenID but no `principalSource` moves from `jwtUnverified` to `jwt` on upgrade, with no values change, so the service verifies tokens itself. Check before upgrading that your callers' tokens pass: an expired token, which `jwtUnverified` accepted, is now refused at the transport (`401` / `UNAUTHENTICATED`); a token whose `aud` is not an accepted audience is refused; and the pods need egress to the identity provider's discovery and JWKS endpoints. A render that succeeds does not prove these.
  - **Migration:** a deployment without an OpenID configuration must add one or set `principalSource` explicitly (`disabled` for a local or test run). A local `uv run start` needs `OMNI_EVENTS_PRINCIPAL_SOURCE=disabled` for a tokenless run (see `BUILDING.md`).
  - **Rollback:** set `principalSource: jwtUnverified` and `allowUnverifiedJwt: true` in the deployment values, but only where every path to the pods verifies tokens first (see the README's trust boundary for `jwtUnverified`).
- **The REST API answers CORS only for configured origins (OMPE-105840, SAST-002).**
  - The service used to answer every origin, with credentials allowed. It now adds CORS only for the origins in `OMNI_EVENTS_CORS_ALLOW_ORIGINS` (Helm `rest.corsAllowOrigins`, default empty, so no CORS) and echoes only those.
  - Write each origin exactly as a browser sends the Origin header: `http` or `https`, an ASCII (punycode) host, no default port (`:80` / `:443`), and no path or trailing slash, for example `https://app.example.com`.
  - The Helm chart refuses at render time only `*`, `null`, a value that is not a list (a plain string included), and an entry that is not a string. The service refuses those two origins and every malformed origin at startup.
  - **Migration:** browser clients that call the service's REST API directly, not through the HTTPProxy's own `httpProxy.corsPolicy`, need their origins listed.

### Fixed
- **The published source ships a `uv.lock` and its `Dockerfile` builds (OMPE-105840, SAST-005).** The published folder under `notifications/reference/event-aggregation-service` now carries a `uv.lock` that pins the versions this release was built and tested with, resolved from public PyPI, with `notification-common` as the sibling `../common` directory. The published `Dockerfile` copies `../common` in through a named build context and installs the locked set, so `docker build --build-context common=../common .` builds the image from that folder. See `BUILDING.md`.
- **The `Dockerfile` installs with `uv export --locked` (OMPE-105840).** A `uv.lock` that is out of date with `pyproject.toml` (or, in the published folder, with the `notification-common` in `../common`) now fails the image build instead of producing an image from the stale lock.
- **The published `uv.lock` matches the `notification-common` published beside it (OMPE-105840).** The service now depends on notification-common 7.0.2, the version published under `notifications/reference/common`. With the previous 7.0.0 pin, `uv sync --locked` and `uv lock --check` in the published folder failed with "The lockfile at `uv.lock` needs to be updated". notification-common 7.0.1 and 7.0.2 change no library code, so the service behaves as before.

### Changed
- **Potentially breaking: per-event limits on both APIs.** Requests that were accepted before can now be refused. A batch may carry at most 1000 events, an event's `message` at most 65536 bytes encoded as JSON, `event_type` at most 256 characters and `resource.resource_id` at most 2048. REST already enforced the batch and string limits; gRPC now enforces all of them, and both APIs now cap the message size. A request over any limit publishes nothing and is answered `422` on REST and `INVALID_ARGUMENT` on gRPC, naming the field (and, in a batch, the event); one oversize event refuses its whole batch. See [Event limits](README.md#event-limits) for how the message size is measured.
- gRPC: the `INVALID_ARGUMENT` details for an event without `occurred_at` now name the event, as `event.occurred_at must be specified` (`PublishEvent`) or `events[<index>].occurred_at must be specified` (`BatchPublishEvents`), instead of `occurred_at must be specified`.
- The source-available release moves to the `NVIDIA-Omniverse/usd-content-workspace` repository. This service's source, `openapi.yaml`, `conformance_tests/`, and the `AGENTS.md` reimplementor guide are published under `notifications/reference/event-aggregation-service`; the publisher Protocol Buffer definitions are published under `notifications/api`, and the customer documentation for both notification services under `notifications/reference/event-consumer-service/docs/`. The published folder includes this service's `.gitignore`. The published `notification-common` dependency resolves from the sibling `notifications/reference/common` directory instead of a git tag. See `BUILDING.md`, which also explains that the published `Dockerfile` does not build from the published folder as-is.

### Fixed
- The Helm chart's `values.yaml` comments for the smoke tests and `permissions.endpoint` now name the settings that control authentication and permission checks (`principalSource`, `permissions.enabled`), and no longer refer readers to a document that is not part of the chart. `permissions.endpoint` is required when `permissions.enabled` is true and ignored otherwise. The smoke-test permission example uses the `event-aggregation-service:publish-event` action, one policy per event type.
- `conformance_tests/docker-compose.yml` now sets `OMNI_EVENTS_REST_PORT` to `8001`, the port its mapping and the suite's REST endpoint use; the image's REST server otherwise binds `8000`. `README.md` now gives `8000` as the `OMNI_EVENTS_REST_PORT` default (`uv run start` defaults it to `8001`).
- The conformance-tests Helm chart's default `service.restEndpoint` and `service.healthEndpoint` now target port `8000`, the service chart's default `rest.port`; they pointed at `8001`, which the service's Kubernetes Service does not expose.
- `conformance_tests/docker-compose.yml` runs its broker on `rabbitmq:4.1.3` (was `rabbitmq:3-alpine`, a release line out of community support).

## [1.6.0] - 2026-09-03

### Added
- The gRPC server now answers the Discovery `CapabilitiesService.ListServices` RPC (`nvidia.omniverse.discovery.capabilities.v2alpha`) on the existing gRPC port, unauthenticated, so the v2 Discovery operator can enumerate this service's APIs dynamically instead of relying on a static registry entry. The response advertises `service_name: "notification-aggregation"`, the service's gRPC endpoints, and — only when the REST API is enabled (`rest_api_enabled`, the default) — a REST endpoint named `notifications-publisher` advertising version `v1beta` at path `/api/v1beta` (the version prefix; the client appends the resource route from the OpenAPI spec). A gRPC-only deployment advertises no REST entry.
- Added a `service.annotations` value to the Helm chart (empty `{}` by default) that renders arbitrary annotations onto the Service object. Set it per-environment to add the discovery selector annotation (`discovery.omniverse.nvidia.com/enabled: "true"`) the v2 Discovery operator scans for, without needing a chart change.
- Added a standardized `observability` block to the Helm chart (OMPE-98173) for configuring OpenTelemetry metrics and tracing over OTLP/gRPC. The `observability.metrics` and `observability.tracing` signals are enabled independently (both default `false`) and read their endpoints from the `.endpoint.grpc` fields; the service is gRPC-only, so the `.endpoint.http` fields are accepted for schema uniformity but ignored. Enabling a signal without its `.endpoint.grpc` set fails chart rendering. Log export ships whenever either signal is enabled (reusing the tracing endpoint, or the metrics endpoint when only metrics is on). The block supersedes the legacy `telemetry` block, which is retained as a backward-compatible fallback — when neither observability signal is enabled, values render identically to before.
- Added two RabbitMQ channel-pool values to the Helm chart: `rabbitmq.channel_overflow_enabled` (default `true`) and `rabbitmq.channel_wait_ms` (default `500`), rendered into the settings ConfigMap as `OMNI_EVENTS_RABBITMQ_CHANNEL_OVERFLOW_ENABLED` and `OMNI_EVENTS_RABBITMQ_CHANNEL_WAIT_MS`. Both defaults match the library's, so a default render preserves currently deployed behavior. Overflow is what makes `rabbitmq.channel_pool_size` × `rabbitmq.channel_client_limit` a *packing threshold* rather than a cap on concurrent publishes — past it, checkouts are packed onto the least-loaded open channel instead of being refused. Set `rabbitmq.channel_overflow_enabled: false` for strict per-request isolation (the pair becomes a hard cap again, and `rabbitmq.channel_wait_ms` becomes the wait for a free slot on a saturated pool). The README env-var table documents both, and its `OMNI_EVENTS_RABBITMQ_CHANNEL_POOL_SIZE` / `OMNI_EVENTS_RABBITMQ_CHANNEL_CLIENT_LIMIT` rows were corrected to the threshold/target semantics.
- **Added a request-body size limit to the REST API.** A request whose body exceeds `OMNI_EVENTS_REST_MAX_REQUEST_BYTES` (default `4194304` — 4 MiB, exposed as the Helm value `rest.maxRequestBytes`) is now refused with `413 Content Too Large` and a `{"detail": "..."}` JSON body naming the limit. The `413` also carries `Connection: close` and the server closes the connection, so a client must not reuse it for a follow-up request. The refusal happens at the edge of the REST stack — before the request is authenticated and before it is parsed — so an oversize request never publishes an event and never reaches the broker, and the service no longer buffers an unbounded body from an unauthenticated caller. Both framings are covered: an oversize `Content-Length` is refused from the header without reading the body, and a chunked upload is refused the moment it passes the limit. The default matches the gRPC API's default 4 MiB inbound message cap so the two APIs refuse at the same bound; keep it well under the broker's `max_message_size` (RabbitMQ's default is 16 MiB), since the published message is larger than the request body — a 4 MiB body can publish as roughly 12 MiB. The limit is independent of the existing 1000-event batch limit: either can refuse a request first, and for events averaging more than about 4 KiB the byte limit binds first. Two consequences of refusing this early: the `413` carries no CORS headers and produces no trace span (the publish API is server-to-server), and each refusal is logged at `WARNING`. `413` is now declared on `POST /api/v1beta/events` and `POST /api/v1beta/events/batch` in the OpenAPI specification, and the limit is documented in the README's new "Request size limit" section and its env-var table. The value must be greater than 0; a zero or negative setting is rejected at startup.
- Added a `shutdown` block to the Helm chart sizing the pod's termination budget: `settleDelaySeconds` (default `15.0`), `drainWindowSeconds` (default `5.0`) and `drainPollIntervalSeconds` (default `0.5`), rendered into the settings ConfigMap as `OMNI_EVENTS_SHUTDOWN_SETTLE_DELAY_SECONDS`, `OMNI_EVENTS_SHUTDOWN_DRAIN_WINDOW_SECONDS` and `OMNI_EVENTS_SHUTDOWN_DRAIN_POLL_INTERVAL_SECONDS`, plus `terminationGracePeriodSeconds` (default `60`), rendered onto the Deployment. Unlike the two `rabbitmq.*` values above, `drainWindowSeconds: 5.0` does **not** preserve the library default: it shortens the effective drain window from `30.0`, and a publish holds a channel for milliseconds, so the 30s window was almost entirely dead time. Termination runs in order: SIGTERM → the `settleDelaySeconds` settle, during which the pod keeps serving normally on both APIs (readiness stays SERVING and new publishes are admitted) so the EndpointSlice → Contour → Envoy de-routing of this readiness-gated Service has time to propagate → bounded drain of in-flight publish checkouts (polled every `drainPollIntervalSeconds`, returning early once none are in flight) → the gRPC and REST servers stop together → the RabbitMQ connector closes. **Pod teardown at the shipped defaults therefore takes about 15s longer**, on every deletion and every rollout; `settleDelaySeconds: 0` skips the phase. The chart enforces one invariant at render time — `terminationGracePeriodSeconds >= settleDelaySeconds + drainWindowSeconds + 10s post-drain teardown` (at defaults `60 >= 15 + 5 + 10 = 30`) — where the 10s term is the fixed cost of the gRPC stop grace and the REST lifespan teardown running concurrently after the drain. **An existing override with `terminationGracePeriodSeconds` below 30 now fails `helm template` / `helm upgrade` instead of rendering.** The render also fails when any `shutdown.*` value, `terminationGracePeriodSeconds` included, is non-numeric, empty, negative, or non-finite (`drainPollIntervalSeconds` must be greater than zero), and when `terminationGracePeriodSeconds` is not a whole number of seconds (Kubernetes takes it as an integer); that bounds check runs first, so such a grace period is named against its own knob rather than reported as a shortfall against the invariant, which is checked last. The settle and drain values may be fractional. The settle is applied by the application itself, so the chart still introduces no Kubernetes-version requirement. See the "Graceful shutdown" section in `README.md`.

### Changed
- **Every publish entry point now authenticates the caller before it inspects the request.** The gRPC `PublishEvent` / `BatchPublishEvents` RPCs and the REST `POST /api/v1beta/events` / `POST /api/v1beta/events/batch` endpoints resolve the caller's bearer token as their first step. **Status codes change for one case:** a request that carries a token the service cannot resolve *and* is also malformed — an empty batch, or a body that fails schema validation — is now answered `401` / `UNAUTHENTICATED`, where it previously returned `400` / `INVALID_ARGUMENT` or `422` because the request-shape check ran first. Requests with valid credentials are unaffected, and no configuration, env var, Helm value, request schema, or response body changes. The full precedence: an unauthenticated or unresolvable caller receives `401` / `UNAUTHENTICATED`, except in two cases — an oversize REST body, which is refused with `413` before authentication, and an oversize gRPC message, the transport-side analogue of that `413`, which the gRPC transport's default 4 MiB inbound message cap rejects with `RESOURCE_EXHAUSTED` on receive, before the RPC handler and the authentication that runs with it. Both are resource limits, not credential decisions; every credential failure, on either transport, is `401` / `UNAUTHENTICATED`. The `principalSource` modes are unchanged — `jwt`, `opaque` and `userInfoService` verify the token as the principal is resolved, while the default `jwtUnverified` decodes the JWT payload without verifying its signature, audience, or expiry and continues to rely on an upstream validator such as Envoy; the set of tokens `jwtUnverified` accepts is unchanged. The intentionally unauthenticated surfaces are untouched (`GET /api/v1beta/health`, the generated docs pages, gRPC health, reflection, and the Discovery `ListServices` call). The token is resolved in the gRPC interceptor and the REST middleware, ahead of the request body — see the `notification-common` `6.12.0` entry below for the status codes and observability that follow from that.
- The Helm chart now sets `terminationGracePeriodSeconds: 60` (previously unset, so the Kubernetes default of 30s applied). **Pod teardown timing changes for every deployment:** worst-case teardown is now 60s, where it was previously capped at 30s, and the typical teardown grows by the `shutdown.settleDelaySeconds` settle (15s at the shipped defaults) during which the pod keeps serving normally. The delay is applied by the application on SIGTERM, not by a pod lifecycle hook, so the chart introduces no Kubernetes-version requirement.
- **Upgraded `notification-common` from `6.10.1` to `6.12.0`** (`pyproject.toml` pin + `uv.lock`), which is where the shutdown and authentication behavior above comes from. Operator- and caller-visible effects:
  - **Both servers now stop at the end of the drain.** The REST listener previously closed as soon as SIGTERM arrived (uvicorn installed its own signal handler), so REST callers routed to a terminating pod saw connection failures while gRPC kept serving; the library now owns both signals and the gRPC and REST servers stop together once the drain returns. The REST teardown consequently runs *after* the drain rather than alongside it, which is what the `+ 10s` term in the grace-period invariant budgets for.
  - **The endpoint-settle phase** backing `shutdown.settleDelaySeconds`; it ships off in the library (`0`) and is turned on by this chart's default of `15.0`.
  - **An unresolvable token is refused before the request body is read.** A REST request that carries such a token and an unparseable JSON body is answered `401`, where it was previously answered `422`.
  - **An IdP outage is no longer reported as a bad credential.** Under `principalSource: jwt`, a failure to *reach* the JWKS endpoint is `500` / `INTERNAL` rather than `401`; an unknown signing-key id remains a `401`.
  - **Upgrade impact — an empty principal claim is now refused.** A caller whose configured `OMNI_EVENTS_PRINCIPAL_ID_CLAIM` resolves to an empty value was previously admitted with an empty identity (the published event simply omitted `principal_identity`) and is now refused with `401` / `UNAUTHENTICATED`. Callers whose claim resolves to a non-empty value are unaffected. A deployment that sees new `401`s after upgrading should check that setting against its IdP's tokens.
  - **`/redoc` and `/docs/oauth2-redirect` are served without an `Authorization` header,** joining `/docs` and `/openapi.json` in the default unauthenticated paths (this service takes the library default and does not override `auth_excluded_paths`).
  - **Observability shifts for anything keyed on auth refusals:** gRPC auth refusals are counted in the `UNAUTHENTICATED` metrics bucket instead of `UNKNOWN`, JWKS-fetch outages land in `INTERNAL`, and a REST auth refusal no longer produces a trace span (the tracing middleware sits inside the auth middleware) and logs a single `WARNING` rather than an `ERROR` with a traceback. gRPC refusals keep both their span and their metrics.

### Removed
- **The REST specification no longer declares a `503` "channel pool exhausted" response** on `POST /api/v1beta/events` or `POST /api/v1beta/events/batch`. The service never produced it: a publish that fails at the broker is reported as `200` with `success: false` and a `failure_reason` in the publishing result, not as an error status — and since `notification-common` 6.6.0 the channel pool packs new checkouts onto already-open channels instead of running out. Clients that special-cased the `503` should handle the documented `200` failure shape instead; nothing else about the responses changes. The gRPC contract is unaffected. (The `413` above is not a replacement for it — it is an unrelated request-size bound, and it is independent of the 1000-event batch limit.)
