## [Unreleased]

### Fixed

The published `Dockerfile` copies `../common` in through a named build context and installs the locked set, so `docker build --build-context common=../common .` builds the image from that folder. See `BUILDING.md`.

With the previous 7.0.0 pin, `uv sync --locked` and `uv lock --check` in the published folder failed with "The lockfile at `uv.lock` needs to be updated". notification-common 7.0.1 and 7.0.2 change no library code, so the service behaves as before.

This service's source, `openapi.yaml`, `conformance_tests/`, the `AGENTS.md` reimplementor guide, and the customer documentation for both notification services (under `docs/`, with the rendered `docs/docs.pdf`) are published under `notifications/reference/event-consumer-service`; the consumer Protocol Buffer definitions are published under `notifications/api`. See `BUILDING.md`, which also explains that the published `Dockerfile` does not build from the published folder as-is.
- The published source now includes this service's `.gitignore`.

### Fixed
- On a non-durable stream with `OMNI_EVENTS_STORAGE_PERMISSIONS_ENABLED`, storage events are delivered for a folder the client may list even when the Storage API lists that folder as empty: the created events in a new or empty folder, the dir-created event for a new folder, and the delete event for a folder's last file. Events under a folder the client may not list (a `403` from the Storage API) are not delivered. When a listing does not authorize a folder, the service logs `storage listing did not authorize a directory; its storage events are dropped until the recheck`, at `INFO` for a `403` and at `WARNING` for a `400` unsupported address or an unrecognized `404`, which usually means a misrouted Storage API endpoint. The number of storage events dropped for such a folder is reported once, in the `dropped_events` attribute of that line or of `storage events were dropped for a directory the storage listing did not authorize`. Neither line names the folder. See the README section "Storage Events With a Non Durable Queue".
- A consume stream whose channel the broker has closed ends with the documented consumer-loss error when the service itself is acknowledging or requeuing an event at that moment, instead of with a generic `Internal Server Error`. On gRPC `ConsumeDurableEvents` the error is `INTERNAL`, and on REST `GET /api/v1beta/events/stream-durable` and `GET /api/v1beta/events/stream` it is an SSE `error` event with status `500`, after which the stream closes; the message is `Internal Server Error: The broker cancelled this stream's consumer. Reconnect to resume consuming.` Reconnect with the same `queue_id` or reconnect token; the error does not by itself confirm that the queue survived, and a queue that is gone answers `NOT_FOUND` / `404` on the reconnect (see the README section "A consume stream ends when the broker drops your consumer"). The same error ends every consume and dead-letter stream when a dropped broker connection interrupts an acknowledgement, a negative acknowledgement, or a dead-letter action.

### Security
- **The service verifies tokens itself by default, and `jwtUnverified` is a deliberate opt-in (OMPE-105840, SAST-001).**
  - Since notification-common 7.0.0 the service refuses to start in `jwtUnverified` mode, which reads the caller's identity from a bearer token without verifying it, unless `OMNI_EVENTS_ALLOW_UNVERIFIED_JWT=true` is also set.
  - The Helm chart's `principalSource` now defaults to empty instead of `jwtUnverified`. An explicit value is used as given. Left empty, the chart selects `jwt`, which verifies every token, when `openId.openIdConfigurationUri` and a JWT audience (a `default` client registration or `openId.additionalJwtAudience`) are configured; without them it refuses to render.
  - The chart never selects `jwtUnverified` by itself: the Envoy auth extension on the HTTPProxy verifies only requests that come through the HTTPProxy, and in-cluster callers can reach the Service directly. `jwtUnverified` renders only when the values set both `principalSource: jwtUnverified` and the new `allowUnverifiedJwt: true`, which is safe only when every path to the pods verifies tokens first (for example a NetworkPolicy that makes the Service unreachable directly).
  - The chart refuses at render time the other authentication settings the service would refuse at startup, so a values file that cannot start fails `helm template` / `helm upgrade` instead of crash-looping the pods: an unknown `principalSource`, `jwt` or `opaque` without their OpenID values, `userInfoService` without `userInfoService.uri`, `disabled` with `permissions.enabled`, `permissions.enabled` without `permissions.endpoint`, more than one `default` client registration, an `openId.additionalJwtAudience` that is not a list, and an `allowUnverifiedJwt` that is not a boolean.
  - **Migration:** a deployment that sets OpenID but no `principalSource` moves from `jwtUnverified` to `jwt` on upgrade, with no values change. Check before upgrading that your callers' tokens pass: an expired token is now refused at the transport (`401` / `UNAUTHENTICATED`), a token whose `aud` is not an accepted audience is refused, and the pods need egress to the identity provider's discovery and JWKS endpoints.
  - **Migration:** a deployment with neither OpenID nor an explicit `principalSource` must set one (`disabled` for a run without tokens). A local `uv run start` needs `OMNI_EVENTS_PRINCIPAL_SOURCE=disabled` (see `BUILDING.md`).
  - **Rollback:** set `principalSource: jwtUnverified` and `allowUnverifiedJwt: true` in the deployment values, but only where every path to the pods verifies tokens first (see the README's trust boundary for `jwtUnverified`).
- **The REST API answers CORS only for configured origins (OMPE-105840, SAST-002).**
  - The service used to answer every origin, with credentials allowed. It now adds CORS only for the origins in `OMNI_EVENTS_CORS_ALLOW_ORIGINS` (Helm `service.rest.corsAllowOrigins`, default empty, so no CORS) and echoes only those.
  - Write each origin exactly as a browser sends the Origin header: `http` or `https`, an ASCII (punycode) host, no default port (`:80` / `:443`), and no path or trailing slash, for example `https://app.example.com`.
  - The Helm chart refuses at render time only `*`, `null`, a value that is not a list, and an entry that is not a string. The service refuses those two origins and every malformed origin at startup.
  - **Migration:** browser clients that call the service's REST API directly, not through the HTTPProxy's own `httpProxy.corsPolicy`, need their origins listed.
- A 401 from the storage API no longer returns the storage API's response body to the client.
- A dead-lettered event whose replay fails reports `republish to the origin queue failed (<exception class>)` in `ActionOutcome.detail` instead of the exception's text.

### Changed (OMPE-105840, GitHub issue #35)
- The OpenAPI document carries the nSpect ID for NVIDIA API governance as the `info.x-nspect.id` extension instead of a top-level `nspect_id` tag, so the document no longer has a top-level `tags` list.
- The package metadata names `NVIDIA` as the author instead of an individual.

## [1.11.0] - 2026-09-18

### Added
- **gRPC `ConsumeNonDurableEvents` acknowledges each filter update it processes.** `ConsumeNonDurableEventsResponse` gains `bool supports_filter_update_acks = 3` and `FilterUpdateAck filter_update_ack = 4`, with a new `FilterUpdateAck { repeated FilterGroup applied_filter_groups = 1; bool unchanged = 2; }` message; the fields are additive, and a client that ignores them sees the stream as before. `supports_filter_update_acks` is `true` on every response of a stream served by a version that acknowledges filter updates, and an acknowledgement is one response carrying no events whose `filter_update_ack` echoes the acknowledged request's `filter_groups` and reports in `unchanged` whether that request's `filter_groups` equalled its `previous_filter_groups` as sent, sent once the bind and unbind calls the request led to have returned. A client that changes filters mid-stream can therefore resume by reconnect token: reconnect with the token, then re-send in order each update it sent but did not see acknowledged, each naming in `previous_filter_groups` the set it replaced. The recipe assumes exactly one client per queue sends filter updates; against a server that does not set `supports_filter_update_acks`, open a fresh stream with `filter_groups` and no `reconnect_token` instead. See the README section "Acknowledged filter updates on a gRPC non-durable stream".
- OMPE-98173: Add standardized `observability` block to the Helm chart for configuring OTEL metrics and tracing via OTLP/gRPC. The metrics and tracing signals are enabled independently and map to the `OMNI_EVENTS_METRICS_ENABLED` / `OMNI_EVENTS_TRACING_ENABLED` env vars the service consumes; log export ships whenever either signal is enabled. The block supersedes the legacy `telemetry` block, which remains as a backward-compatible fallback (values without an enabled `observability` block render identically to before).
- `CreateDurableQueue` now accepts an optional client-specified `queue_id`, making durable queue creation idempotent (ensure-exists). Supplied on the gRPC `CreateDurableQueueRequest` (`queue_id`) or in the REST request body, it must match `^[A-Za-z0-9._-]{1,200}$`. If a queue with that id already exists it is returned unchanged, bound to its existing filters, regardless of who created it or which `filter_groups` are passed; otherwise it is created. Queue ids share one deployment-wide namespace, so a client-chosen `queue_id` must be unique across the deployment — use a UUID or a namespaced convention such as `<service-name>-<purpose>`; two callers that pick the same id share one queue, and either can delete it. When `queue_id` is omitted, behavior is unchanged and the server generates one.
- New `created` field on `CreateDurableQueueResponse` (gRPC `bool created`; REST `created`) indicating whether the queue was newly created (`true`) or already existed and was returned unchanged (`false`).
- The gRPC server now serves the discovery `CapabilitiesService.ListServices` RPC (`nvidia.omniverse.discovery.capabilities.v2alpha`), a new unauthenticated endpoint that lets the Omniverse Discovery platform enumerate this deployment's advertised APIs. `ListServices` reports the discovery type `notification-consumer`, the gRPC `EventConsumerService`, and — only when the REST surface is enabled — a single `RestEndpoint` named `notifications-consumer` at `/api/v1beta` (the OpenAPI spec base path). Discovery is opt-in per environment via a new empty-by-default `service.annotations` value on the main Kubernetes `Service` in the Helm chart (set `discovery.omniverse.nvidia.com/enabled: "true"` to register the deployment with the Discovery operator).

- `ConsumeDurableEventsWithAcksRequest` gains `repeated int64 nack_delivery_tags = 3` (gRPC). A nacked message is requeued and redelivered immediately, possibly on the same stream; acks are processed before nacks, so a tag in both lists is acknowledged; unknown or already-settled tags are skipped without terminating the stream. Redelivery counts are cumulative over the message's lifetime — a nack, a disconnect, and a broker channel close each increment it — and a message whose count exceeds the deployment's delivery limit is moved to the dead-letter queue.
- Consumer-loss error contract on every consume stream (gRPC and REST/SSE, durable and non-durable). When the broker drops a stream's consumer, the stream now ends promptly with a classified error instead of hanging idle: `NOT_FOUND` (REST `404`) when the queue no longer exists — recreate it via `CreateDurableQueue` (durable) or open a fresh stream (non-durable) — or `INTERNAL` (REST `500`) with the message `Internal Server Error: The broker cancelled this stream's consumer. Reconnect to resume consuming.` when the queue survives — reconnect with the same `queue_id` / `reconnect_token`.
- REST `GET /api/v1beta/events/stream`: the `Last-Event-ID` request header is now documented in the OpenAPI schema as the recommended carrier for a reconnect token (browsers send it automatically during SSE reconnection). It carries exactly the value the `reconnect_token` query parameter would, and supports the same operations. Sending `previous_filter_groups` together with `filter_groups` is what makes a request a filter update, whichever carrier the token arrives in; a request that carries the token alone resumes the stream on the filters it already has. A browser's automatic SSE reconnect replays the URL the stream was opened on and sends the token in the `Last-Event-ID` header, so when that URL carried only the initial `filter_groups`, the header path resumes as-is.
- Helm chart: `policyHook` block that applies the durable-queue RabbitMQ policy (`event-queue-limits`: `deliveryLimit`, `messageTtlMs`, `maxLength`, `overflow`, `expiresMs`, optional `consumerTimeoutMs`) through the broker management API from a post-install/post-upgrade hook Job, with `managementApi.{baseUrl,vhost,existingSecret}` inputs. New `service.grpc.healthCheckingEnabled` and `rabbitmq.non_durable_queue_ttl_seconds` values.
- Helm chart: `shutdown` block giving a terminating pod an orderly hand-off of its live consumer streams instead of a force-drop. On SIGTERM the pod keeps serving normally — readiness still `SERVING`, new streams still admitted — for `shutdown.settleDelaySeconds` (default `15`), which is the budget for the endpoint change to reach clients that dial the readiness-gated main Service directly; `0` skips the phase. It then enters a draining state, where readiness flips to `NOT_SERVING` and *new* non-durable streams are refused (HTTP `503` on REST, `RESOURCE_EXHAUSTED` on gRPC, re-routed to another ready pod by the streaming routes' retry policy) while its already-admitted in-flight streams keep serving, and waits up to `shutdown.drainWindowSeconds` (default `30`) for them to finish, re-reading the in-flight count every `shutdown.drainPollIntervalSeconds` (default `0.5`) so it can close early. `shutdown.terminationGracePeriodSeconds` (default `60`) is the total budget from pod deletion to SIGKILL, and the chart enforces `terminationGracePeriodSeconds >= settleDelaySeconds + drainWindowSeconds + 10` at render time, where the added 10 seconds is the fixed post-drain server teardown. That bound is a floor rather than a guarantee: the teardown's wait for open REST/SSE connections is unbounded and deliberately not budgeted, so raise the grace period above the floor if your deployment holds idle REST/SSE streams when a pod is deleted. See the README section "Graceful drain on scale-down and rollout".

### Changed
- **The bearer token is validated before the operation it authorizes begins**, on both the gRPC and the REST surface. The shared gRPC interceptor and the shared REST middleware resolve the token through the configured `OMNI_EVENTS_PRINCIPAL_SOURCE` ahead of any handler and refuse one they cannot resolve with `UNAUTHENTICATED` / `401`. An unresolvable token was already refused on every authenticated operation; what moved is where the refusal happens, not whether it happens. Which modes *verify* a token is unchanged: `jwt`, `opaque`, and `userInfoService` verify as they resolve, while the default `jwtUnverified` decodes the JWT payload only and continues to rely on an upstream validator such as Envoy.
- **A token whose configured principal claim is present but empty is rejected** with `UNAUTHENTICATED` / `401`, as a token missing the claim entirely already was. Such a token was previously accepted and admitted with an empty principal identity. **Upgrade note:** a deployment whose identity provider issues an empty value for `OMNI_EVENTS_PRINCIPAL_ID_CLAIM` must point that setting at a claim its tokens actually carry.
- **An unreachable identity provider is reported as `INTERNAL` / `500` rather than as an authentication failure.** With `OMNI_EVENTS_PRINCIPAL_SOURCE=jwt`, a failure to fetch the provider's JWKS is a server error, so callers are not sent to check their credentials during a provider outage. A token whose key id the provider does not publish is still `UNAUTHENTICATED` / `401`.
- **A request carrying an unresolvable bearer token to a pod that is at its stream capacity is answered as an authentication failure**, not with the capacity contract: `UNAUTHENTICATED` / `401` rather than `RESOURCE_EXHAUSTED` / `503`, and the ingress does not retry it onto another pod, because the same token is refused on every pod. A request whose token resolves is unaffected: it is still refused with `RESOURCE_EXHAUSTED` / `503` and, on the streaming routes whose retry policy keys on it, still retried.
- **`GET /redoc` and `GET /docs/oauth2-redirect` are served without a bearer token**, alongside `GET /docs` and `GET /openapi.json`; all four serve generated API documentation and nothing else. The two health endpoints and the two `/metrics/channel-pool` endpoints continue to serve without a token. The README section "Endpoints served without a bearer token" lists the full set.
- **Observability of authentication refusals moves with the status codes.** A refusal is logged once at `WARNING` on both surfaces (`Rejecting request with an unresolvable token: …`). gRPC refusals are recorded under `UNAUTHENTICATED` instead of the `UNKNOWN` error bucket, and JWKS-fetch outages under `INTERNAL`, so dashboards and alerts keyed on the old buckets must move. A REST request refused by authentication produces no trace span, because the authentication check runs ahead of the tracing middleware; gRPC refusals keep their span and metrics.
- REST `POST /api/v1beta/events/durable-queue` status codes: returns `200` when no `queue_id` is supplied (server-generated id) or when a supplied `queue_id` matched an existing queue (`created=false`); returns `201` when a supplied `queue_id` created a new queue (`created=true`); returns `422` when a supplied `queue_id` fails pattern validation.
- gRPC `CreateDurableQueue` returns `INVALID_ARGUMENT` when a supplied `queue_id` fails pattern validation.
- **Durable queue names no longer embed the caller's identity.** A durable queue's broker name is `event-queue:<queue_id>`; a change to a client's identity (identity-provider migration, re-created service account, a different principal claim) can no longer orphan its queues. Consequences: `queue_id` values share one deployment-wide namespace (see the `CreateDurableQueue` entry above), and per-queue isolation is not enforced — the three durable-queue permissions (`consume-durable-queues`, `create-durable-queues`, which also authorizes `UpdateDurableQueue`, and `delete-durable-queues`) are deployment-wide, so grant them deliberately to service accounts rather than broad user groups. **Upgrade note:** durable queues created by earlier versions carry the old identity-derived name and are not reachable after upgrading; recreate them with `CreateDurableQueue` (a reaped or missing queue returns `NOT_FOUND` / `404` on consume). The consume, consume-with-acks, update, and delete requests document that the supplied `queue_id` must be the id of a queue created by (or for) your client.
- `queue_id` is validated against `^[A-Za-z0-9._-]{1,200}$` on every durable operation, not only on create: `ConsumeDurableEvents`, `ConsumeDurableEventsWithAcks`, `UpdateDurableQueue`, and `DeleteDurableQueue` return `INVALID_ARGUMENT`, and REST `GET /api/v1beta/events/stream-durable`, `PATCH /api/v1beta/queues/durable`, and `DELETE /api/v1beta/queues/durable` return `422`, for an id that does not match. `stream-durable`'s previously documented `400 Invalid queue_id parameter` is replaced by that `422`.
- `reconnect_token` must be 1 to 200 printable ASCII characters (no spaces, control characters, or non-ASCII), on the gRPC request field, the REST `reconnect_token` query parameter (previously up to 1024 characters), and the `Last-Event-ID` header (previously unbounded); anything else is rejected with `INVALID_ARGUMENT` / `422`. Tokens issued by the service are UUIDs and always satisfy the rule. The REST `reconnect_token` query parameter is deprecated in favour of the `Last-Event-ID` header; it remains accepted and carries the token the same way. A second principal that attaches to a non-durable queue with the same reconnect token is authorized from its own permissions and, with `OMNI_EVENTS_REDIS_ENABLED`, builds its own cached authorization state; neither principal's attach interrupts the other's stream. Several clients authenticating as the same principal and sharing one token share one cache and split the queue's events between them.
- Durable queues expire after 24 hours without a consumer (chart default `policyHook.policy.definition.expiresMs: 86400000`, applied as a broker policy so it can be retuned on running queues). A client must persist both its `queue_id` and the filter groups it created the queue with: a reaped queue is recreated empty via ensure-exists, bound to the filters the recreate call carries.
- `OMNI_EVENTS_DEAD_LETTER_QUEUE_*` bound settings apply at queue creation only. Changing them on an existing deployment no longer crash-loops the service; the service logs one `Dead-letter queue argument mismatch` ERROR per (re)connect and continues against the live queue's bounds. See the README section "Retuning the dead-letter queue's bounds".
- Helm chart: the endpoint-settle delay at the start of shutdown is now applied by the application rather than by a Kubernetes `lifecycle.preStop.sleep` handler. This affects deployments running an earlier build from the 1.11.0 development cycle, where the delay was rendered as that handler; no released version carried it. The chart value `shutdown.preStopDelaySeconds` is replaced by `shutdown.settleDelaySeconds` (same meaning, same default of 15), which renders `OMNI_EVENTS_SHUTDOWN_SETTLE_DELAY_SECONDS` into the settings ConfigMap beside the drain settings. A values file that still sets `shutdown.preStopDelaySeconds` is rejected at render time with a message naming the new key, so an upgrade cannot silently drop a tuned value.
- Helm chart: the grace-period bound the chart enforces at render time (stated in full in the `shutdown` block entry above) is 10 seconds higher for the same settle and drain values. The shipped default grace period is unchanged at 60. **A deployment that had tuned the grace period to the previous two-term bound must re-check it**: a values file below the new bound fails the render. The same check also rejects a negative or non-numeric `shutdown.settleDelaySeconds` or `shutdown.drainWindowSeconds`, and a `shutdown.drainPollIntervalSeconds` that is not greater than zero.
- Observability: for non-durable streams, the span attribute and the `cache_writer.*` metric attribute `queue_id` are renamed `queue_ref` and carry a stable, non-reversible `sha256-<12 hex>` reference instead of the reconnect token; the service's logs and its own HTTP access log identify a non-durable stream the same way. Dashboards keyed on the old attribute must move to `queue_ref`. Durable streams keep `queue_id`.

### Deprecated
- REST `GET /api/v1beta/events/stream`: the `reconnect_token` query parameter is deprecated in favor of the `Last-Event-ID` request header, which carries the same value and supports the same operations (plain resume and filter update). The parameter is still accepted, behaves exactly as before, and is marked `deprecated` in the OpenAPI schema as guidance; no removal is scheduled. Query strings are routinely recorded by proxies, gateways, and browser history, so moving the token into a header keeps it out of those logs.

### Removed
- `OMNI_EVENTS_CONSUMER_TIMEOUT_MS` setting. The consumer ack timeout is a RabbitMQ `consumer-timeout` policy, now configured through `policyHook.policy.definition.consumerTimeoutMs` in the chart (default unset; minimum `60000`). The old variable is ignored.

### Fixed
- **In the default `jwtUnverified` mode, a token past its own expiry no longer fails part-way through a request.** That mode accepts an expired token deliberately, leaving token validity to the upstream validator that fronts the service. Such a token was accepted when the request arrived and then rejected with `UNAUTHENTICATED` / `401` by `CreateDurableQueue` and by a non-durable stream attach — the two operations that resolve the caller's identity a second time. Both complete.
- gRPC `ManageDeadLetteredEvents` streams reached through the Helm chart's `HTTPProxy` ingress are no longer severed by the catch-all route's short idle timeout. The chart renders a dedicated streaming route for `ManageDeadLetteredEvents`, so a dead-letter management stream carries the streaming routes' long timeout envelope instead of the catch-all route's configurable timeouts (`httpProxy.timeoutPolicy`, default `10s` response and idle), and it receives those routes' retry and load-balancing policies (`httpProxy.streaming.*`).
- Unary calls — durable-queue create, update, and delete, on both the REST and the gRPC surface — reached through the Helm chart's `HTTPProxy` ingress are retried by the proxy when the selected pod refuses the connection or refuses the HTTP/2 stream, the two failure classes a rolling upgrade produces and in which the request never reached an application. Configured by `httpProxy.unary.retryPolicy.enabled` (default `true`) and `httpProxy.unary.retryPolicy.count` (default `3`), overridable per protocol under `httpProxy.grpc.unary.*` and `httpProxy.rest.unary.*`; set `enabled: false` to disable. The retry conditions are fixed and deliberately narrow: no response status is retried, so a request the service has already processed is never replayed. On the REST surface, HTTP/1.1 offers no equivalent of the stream refusal, so a request dispatched onto a connection the departing pod has already closed still surfaces to the client. A client may retry a lone `503` itself: on update and delete as-is — a repeated delete answers `NOT_FOUND` (REST `404`) when the first attempt did land, which is the success case, the queue is gone, and not a failure — and on create only when it supplied its own `queue_id`, which makes creation ensure-exists. Retrying a create that omitted `queue_id` leaves a second, orphaned queue behind.
- Helm chart: installs and upgrades no longer fail on Kubernetes clusters where the `PodLifecycleSleepAction` feature gate is unavailable or turned off. This affects deployments running an earlier build from the 1.11.0 development cycle, where the Deployment rendered a `lifecycle.preStop.sleep` handler; no released version carried it. Such an API server strips that handler before validation, rejecting the pod with `must specify a handler type` and producing a ReplicaSet that cannot start pods. The Deployment now carries no `lifecycle` block, so the chart installs on any Kubernetes version the rest of the chart supports, and the chart declares no version floor on this account.
- REST calls to a terminating pod keep working for the whole drain window instead of failing from SIGTERM onward. The REST server previously began its own teardown the moment the pod received SIGTERM, concurrently with the drain, so the "keeps serving its in-flight streams and refuses only *new* non-durable streams with `503`" contract held on gRPC but not on REST; both surfaces now stop together at the end of the drain, and the contract holds on each.
- The chart's post-upgrade smoke tests tolerate transient connection failures, `503`s, and gRPC `UNAVAILABLE` while a rollout settles: the durable-queue create, update, and delete checks retry within a bounded budget and supply a client-generated `queue_id`, so a retried create is idempotent rather than a duplicate.

## [1.10.0] - 2026-06-24

### Added
- New gRPC `ConsumeDurableEventsWithAcks` RPC for durable queue consumption with explicit client acknowledgment via bidirectional streaming, with dedicated `ConsumeDurableEventsWithAcksRequest` and `ConsumeDurableEventsWithAcksResponse` message types. Clients receive events with a `delivery_tag` and send acknowledgments back on the same stream. Unacknowledged messages are redelivered on reconnect.
- New gRPC `ManageDeadLetteredEvents` RPC for operator inspection and replay of dead-lettered events, via bidirectional streaming. The server streams `DeadLetteredEvent` messages — each carrying the original `event`, the `reason` it was dead-lettered (`DELIVERY_LIMIT`, `EXPIRED`, or `MAXLEN`), its origin queue, delivery count, and a session-scoped `delivery_tag` — and the client streams back per-message `REPLAY` (republish to the original queue), `DISCARD`, or `LEAVE` decisions, each answered with an `ActionOutcome` (`REPLAYED`, `DISCARDED`, `LEFT`, `ORIGIN_QUEUE_DELETED`, or `REPLAY_FAILED`). Requires the `inspect-and-replay-all-dlq` permission.

### Changed
- Durable-queue events that exhaust their delivery limit, expire, or overflow the queue's max length are now **dead-lettered** (preserved for inspection and replay via the new `ManageDeadLetteredEvents` RPC) instead of being dropped or redelivered indefinitely. Durable queues are now backed by quorum queues for bounded, delivery-count-tracked redelivery. This requires a RabbitMQ 4.x broker.
- REST SSE durable stream (`GET /api/v1beta/events/stream-durable`) now uses server-side delayed acknowledgment. Messages are automatically acknowledged by the server after a short delay. The `session_id` and `delivery_tag` fields are no longer included in SSE event payloads. Clients requiring explicit per-message acknowledgment should use the gRPC `ConsumeDurableEventsWithAcks` RPC.

### Removed
- `POST /api/v1beta/events/ack-durable` endpoint has been removed. Client-side acknowledgment of durable events is only available via gRPC.

### Deprecated
- gRPC `ConsumeDurableEvents` RPC is deprecated in favor of `ConsumeDurableEventsWithAcks`. The existing RPC signature is preserved (unary request, server-streaming response) for backwards compatibility, but will be removed in a future release.
