# Path C: a Rust adapter on Storage Core

> **Applies to:** Rust services built on the `storage-core` crates · **Released:** library only; not a separate NGC artifact. The crates are pre-1.0 alpha libraries; released Storage Service **1.2.3** records the versions it uses in [`storage-service/CHANGELOG.md`](../../../../../storage/reference/storage-service/CHANGELOG.md) `[1.2.3]` · **This repo's snapshot:** the source commit in [`SOURCE_VERSIONS.md`](../../../../../SOURCE_VERSIONS.md); `Cargo.toml` still holds the versions 1.2.3 shipped with, but the code has unreleased, **breaking** trait changes that the Storage Service records as a Storage Core update ([components/storage-core.md](../../components/storage-core.md#released-versus-snapshot)); `rust-version = "1.91.1"` · **Sources:** [`storage/reference/storage-core/docs/`](../../../../../storage/reference/storage-core/docs/), [`examples/`](../../../../../storage/reference/storage-core/examples/), `storage-core-builder/src/traits/`, Storage Service `storage-service/src/api/discovery/`, upstream storage-core skill (the [source skill package](../../../NOTICE.md) pin)

Storage Core is the Rust framework under the Storage Service. It serves gRPC and REST for the Storage API from one implementation, and composes **layers** (caching, throttling, metrics, routing, header injection) around a **backend**. Writing a backend gives your storage the same operational stack the S3 and Azure backends use. Component map: [components/storage-core.md](../../components/storage-core.md).

## How the pieces fit

| Concept | Where | Notes |
|---|---|---|
| Per-API traits | `storage_core_builder::traits::{fileobject,filefolder,capabilities,versioning}::{v1alpha,v1beta}`, `metadata::v1alpha` | Generated by a macro; every method has a default |
| Backend | Your type implementing those traits | `fn inner(&self) -> Option<&dyn Trait>` returns `None`, so unimplemented methods return `Unimplemented` |
| Layer | Type wrapping an inner service | Returns `Some(inner)`; overrides only what it changes ([`docs/layers.md`](../../../../../storage/reference/storage-core/docs/layers.md)) |
| Builders | `FileObjectBuilder`, `FileFolderBuilder`, `CapabilitiesBuilder`, `VersioningBuilder`, … | `.layer(...)`, `.option_layer(...)`, `.backend(...)` |
| Server | `StorageService::builder().add_service(...).serve(grpc_addr, http_addr, metrics)` | `ListServices` is generated from the registered services; backends do not implement it |
| Errors | `StorageErrorExt` (`tonic_status`, `http_status`, `get_size`) | [`docs/errors.md`](../../../../../storage/reference/storage-core/docs/errors.md) lists the errors each RPC returns |
| Config and secrets | `figment`; `storage_core_util::secrets::Secrets` | [`docs/configuration.md`](../../../../../storage/reference/storage-core/docs/configuration.md), [`docs/secrets.md`](../../../../../storage/reference/storage-core/docs/secrets.md) |

Trait signatures differ from the protos in places: `write` receives `WriteParameters` plus a `BoxFuture<Bytes>`, and `enumerate` takes `StreamingOptions` and returns items with a continuation token ([`traits/fileobject.rs`](../../../../../storage/reference/storage-core/storage-core-builder/src/traits/fileobject.rs)). In this snapshot the `write` body future yields exactly `data_object_size` bytes: the ingress fails a shorter body with `INVALID_ARGUMENT` and drops bytes past the declared size before your backend sees them.

Signature rules in this snapshot ([`docs/architecture.md` "Trait method conventions"](../../../../../storage/reference/storage-core/docs/architecture.md#trait-method-conventions)). They matter when you declare a new trait method (for a new service, as in `greeter_service`); `generate_storage_trait!` rejects violating parameters at compile time, but not return types:

- Every method takes `request: Request<FooRequest>` first and returns `Result<FooResponse>` (or a stream). The only other parameters allowed are `StreamingOptions`, the `write` body `BoxFuture<Bytes>`, and `enumerate_versions`'s grandfathered `version_id_token: Option<String>`.
- Caller metadata (credentials, tracing headers) is in `request.metadata()`. Layer-derived context is in `request.extensions()`: take `AdditionalHeaders` with `request.extensions_mut().remove::<AdditionalHeaders>()`, and in `read`/`read_from_address` take a cached `ResourceInfo` the same way instead of issuing your own stat ([`docs/backends.md`](../../../../../storage/reference/storage-core/docs/backends.md)).
- Never build an empty `MetadataMap`, `Extensions` or `Request` below the ingress; that silently drops the caller's credentials. For a sub-request, build it from the incoming request's parts. `storage-core/tests/no_fabricated_request_context.rs` enforces this inside Storage Core; apply the same rule in your crate.
- **Migration from the Storage Core in released Storage Service 1.2.3:** `Versioning::is_versioning_enabled` was removed from both trait versions. Implement v1alpha `is_versioned(&self, request: Request<IsVersionedRequest>) -> Result<IsVersionedResponse>`; there is nothing to replace it with in v1beta.

## Steps

1. Read [`docs/architecture.md`](../../../../../storage/reference/storage-core/docs/architecture.md), then [`docs/backends.md`](../../../../../storage/reference/storage-core/docs/backends.md).
2. Implement the traits for the API versions you will serve ([capabilities-and-versioning.md](capabilities-and-versioning.md#what-to-serve)). Start with `fileobject::v1beta::FileObject::stat`; return `None` from `inner()`.
3. Map backend errors through `StorageErrorExt` so gRPC and REST codes match [the contract](production-implementation.md#error-mapping).
4. Build configuration with `figment` under your own key, and load credentials through `Secrets` from a mounted Kubernetes Secret or workload identity ([`docs/secrets.md`](../../../../../storage/reference/storage-core/docs/secrets.md#kubernetes-deployment)), never from source or values files.
5. Register the services and serve:

```rust
StorageService::builder()
    .add_service(FileObjectBuilder::new().backend(backend.clone()))
    .add_service(FileFolderBuilder::new().backend(backend.clone()))
    .add_service(CapabilitiesBuilder::new().backend(backend.clone()))
    .add_service(VersioningBuilder::new().backend(backend.clone()))
    .serve(Some(grpc_addr), Some(http_addr), None)
    .await?;
```

6. Add layers you need (stat cache, list cache, small-object cache, egress throttle, metrics, additional headers): [`docs/applications.md`](../../../../../storage/reference/storage-core/docs/applications.md#layer-configuration). Features gate them (`stat_cache`, `list_cache`, `small_object_cache`, `egress_throttle`, `metrics`, `additional_headers`, `manifest`, …; `full` = `backends` + `layers`) in [`storage-core/Cargo.toml`](../../../../../storage/reference/storage-core/storage-core/Cargo.toml).
7. Add the Discovery capabilities service (below) and a gRPC health service.
8. Run the Storage API conformance suite against the binary ([test/conformance.md](../../test/conformance.md#storage-api-conformance-suite)).

The "Complete Example" in [`docs/backends.md`](../../../../../storage/reference/storage-core/docs/backends.md#complete-example) is illustrative, not compilable: `new` is a synchronous function that uses `.await`, and `resolve_path` joins the caller's address onto the root without rejecting `..`. Validate and contain paths yourself.

## Serving extra gRPC services

Anything implementing `ToGrpcService + ToRestService + ServiceInfoProvider` can be passed to `add_service`. Two in-repo examples:

- [`examples/greeter_service/`](../../../../../storage/reference/storage-core/examples/greeter_service/README.md): a wholly new service with its own proto, trait, backend, ingresses and builder.
- The Storage Service's Discovery capabilities: [`storage-service/src/api/discovery/grpc.rs`](../../../../../storage/reference/storage-service/storage-service/src/api/discovery/grpc.rs) implements `nvidia.omniverse.discovery.capabilities.v2alpha.CapabilitiesService` through `ToGrpcService`. Storage Core itself does not serve the Discovery API; without it the Auto Discovery operator cannot register your binary ([develop/add-your-service.md](../add-your-service.md#expose-discovery-capabilities)).

## Building and testing the workspace

From `storage/reference/storage-core/` (no `rust-toolchain.toml` here; use Rust ≥ 1.91.1). `storage-core-protos` uses a vendored `protoc` (`protoc-bin-vendored`), so no system `protoc` is needed. The workspace patches `azure_*` crates to the NVIDIA fork vendored at [`storage/reference/externals/azure-sdk/`](../../../../../storage/reference/externals/azure-sdk/), so build it inside this repository layout.

```bash
cd storage/reference/storage-core
cargo build -p storage-core --features full
cargo run -p basic-service --bin basic-s3 -- --config config.toml   # or --bin basic-azure
cargo nextest run --workspace                                       # unit tests + small integration subset
```

[`examples/basic/README.md`](../../../../../storage/reference/storage-core/examples/basic/README.md) says `azure` is the default feature and the two cannot be combined; its `Cargo.toml` enables both by default and builds separate `basic-azure` and `basic-s3` binaries. Its "How the Remapper Works" section belongs to [`examples/remapper/`](../../../../../storage/reference/storage-core/examples/remapper/README.md). The examples default to gRPC `0.0.0.0:50051` and HTTP `0.0.0.0:8011`.

Integration tiers and their prerequisites are in [test/conformance.md](../../test/conformance.md#storage-core-integration-tests).

## Pinning the protos

Storage Core compiles its own copy of the Storage API protos ([`storage-core-protos/proto/storage-protos/VERSION`](../../../../../storage/reference/storage-core/storage-core-protos/proto/storage-protos/VERSION)): storage-protos tag 0.28.0 plus hand-applied native-metadata hunks and local `IsReadOnly`/`IsVersioned` RPCs. The file now records that those two RPCs were added upstream in unreleased Storage API source; the crate has not been re-vendored from it. Do not re-vendor from the 0.28.0 tag without reading that file; doing so deletes RPCs every consumer depends on. A backend built here serves that pinned contract, not necessarily the one in `storage/api/proto`; check the differences in [apis/storage.md](../../apis/storage.md#copies-of-the-contract-inside-implementations).

The upstream skill says the crates publish to an internal Cargo registry with exact pins. In this repository consumers use path dependencies (the Storage Service's `Cargo.toml` points at `../storage-core/...`); registry publication is unverified here.
